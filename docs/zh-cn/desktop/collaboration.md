# 群聊与 Named Agent 协作

Named Agent 协作让人和具有长期身份的 Agent 在频道、私聊中一起工作。匿名子代理仍是独立的
临时委派路径，适合边界清楚的子任务，详见[Agent 协作与子代理](subagents.md)。

## 房间、身份与 session

每个频道拥有一个隐藏协调者。协调上下文、任务分配和进度属于这个房间。协调者不进入成员
列表，也不以新的人格在群里发言。可见的 Named Agent 负责执行和交付。

Named Agent 有稳定的名字、头像、角色、模型配置、成员关系和私有长期记忆。
**同一个身份可以有多个独立 session。** 每个 session 有自己的模型上下文、目标、执行和
恢复状态。不相关的工作可以在同一个名字下面分别运行；新建 session 不会创建新的公开身份，
也不会清除这个身份的记忆。

协调者可以读取项目文件、搜索证据、查看房间消息和 session 状态，并管理任务分配。它不能
修改文件、执行 shell 命令、加载任意执行工具、读取成员的私有收件箱或冒充成员。它继承当前
模型配置；执行 session 使用所属 Named Agent 的 provider/model 配置，并受主机的工作区与
权限边界约束。

## 一条消息会唤醒谁

路由优先保留用户明确指定的接收者：

- 私聊直接交给对应 Named Agent 在该房间的 conversation session。
- 明确提及成员或回复 Agent 时，消息交给对应成员；`@all` 明确选择所有成员。
- Task Thread 中未指定接收者的补充交给当前任务负责人。
- 只有一个 Agent 的频道，未点名消息直接交给该成员。
- 有多个 Agent 的频道，未点名消息只唤醒该房间的协调者。

协调者读取请求、成员目录和已有工作，选择一个负责人。默认先由一人负责，只有工作能够独立
推进时才创建并行 session。成员保留房间上下文，但新消息本身不会启动所有成员。Agent 的
普通公开回复也不会自动唤醒协调者，或触发下一轮互相确认。

## 对话、工作与验证

简单问题通过 `collaboration_send` 私下交给成员的房间 conversation session，由成员公开
回答。普通对话不要求创建 Task 或进行验收。

较大的工作可以通过 `chat_session` 在指定成员下面创建 session，或通过 `chat_task` 建立
有可见负责人的持久任务。Session 有明确目标和稳定的请求 ID，同一个创建请求重试不会重复
派工。任务目标、负责人、版本、运行记录和产物会持久保存。目标或成员变化后，协调者可以在
本房间内补充要求、停止、恢复或重新分配工作。

委派是异步的。协调者派工后结束当前模型回合并释放运行槽位；新的用户输入和子 session 的
完成、失败等终态事件可以再次唤醒它。它根据结果推进依赖步骤，让负责人报告进度并交付。
协调者自己的最终文字保留在私有上下文中。

验证按需使用。任务要求验证时，由另一 Named Agent 的 verifier run 检查当前候选，并记录
绑定目标和候选版本的判决。负责人处理修订和公开交付。普通对话和每次交付不会默认创建一个
隐藏验收者。

## 创建和管理 Agent

进入**协作**后，创建 Named Agent，再创建或加入频道。首次打开功能不会自动创建默认身份
或频道。Agent 管理提供以下配置：

- **名字与头像**：公开身份。
- **角色**：选择负责人时参考的专长。
- **模型**：继承当前 provider/model，或指定模型与 thinking effort。
- **Autostart**：收到可处理事件后是否自动开始执行。

重置对话保留身份和长期记忆。删除 Agent 后，不再向该身份分配新工作。每个频道最多 32 名
成员，其中 Named Agent 最多 6 个。私聊使用独立的私有房间。

## 状态与恢复

输入框上方用独立的小黑球表达协调过程，成员开始执行后由对应头像的活动动画接续。正常运行
不显示常驻的名字或状态文字；悬停可查看身份和状态，点击执行中的成员头像可查看轨迹。
排队、等待使用安静的表情，工作使用轻微动作，完成后淡出。系统开启减少动态效果时停止这些
过渡和循环动画。失败时保留原因与重试入口，空房间保留添加成员的提示。协调者不进入成员
列表，也不作为公开执行 session 展示。

默认并发上限为每个身份 5 个、每个房间 12 个、全局 24 个启动中或运行中的执行。Work run
和独立协作 session 共用容量；协调者也受房间与全局上限约束。排队、等待、空闲和历史 session
不占执行槽位。待处理工作会持久排队。

消息、分配、私有投递、session 绑定和终态结果在重启后保留。恢复过程重新核对待处理工作，
结果返回发起它的 session 或任务分配路径。协调者发生模型服务故障后可以重试，原请求不会
因此广播给所有成员。恢复不保证中断的模型输出能从同一个 token 位置继续。

## 消息与私下交接

房间消息按序列号排序，可以包含文本、图片、文件、任务或系统事件。文本消息上限为 4000
字符。回复保留来源消息关系，任务讨论保留所在 Thread。

`chat_check` 拉取有权访问的收件箱条目，`chat_read` 读取正文或房间内的序列范围。私下交接
记录发送者、接收者、来源 session、可选目标 session，以及关联的 Work 版本。主机在投递前
校验成员关系、session 归属和版本。协调者不能利用本房间权限读取其他房间的历史或成员的
私有收件箱。

成员通过 `chat_send` 公开发言时，`basis_seq` 新鲜度检查可能将过时回复暂存为草稿；成员用
`chat_draft` 在读到新消息后发布或放弃。私有控制消息和 session 终态结果使用持久投递，
无需在公开群聊里互相确认。

## 长期安排与记忆

房间右上角的「安排与记忆」可以查看后续安排，暂停、恢复或取消，也可以查看、编辑和删除
房间共享记忆或成员的身份记忆。安排由模型通过 `chat_wake` 保存；支持一次性、带时区的
周期安排，以及等待另一个会话结束后继续。简单提醒可以直接发群消息，无需再次调用模型。

会话安排回到原会话继续，停止会话会取消它及其子会话的安排。身份或房间安排独立于创建
它的那一次执行，长期职责可以在后续执行中继续。等待不占执行槽位；到期后沿用现有排队
机制。修改、暂停或取消会撤回尚未接收的投递，不会撤销已经开始执行的操作。安排引用的
任务结束、目标版本改变或成员失去房间权限时，系统阻止过时的安排继续执行。

安排和投递一起持久保存，重启不会重复创建同一次提醒。周期安排合并离线期间错过的次数，
同一安排已有未处理唤醒时也不会不断积压。**执行主机必须运行**：设备关机、休眠或 Wuu
退出时不能按时发送；恢复后处理到期安排。这套机制不提供云端常驻执行或离线推送。

`chat_memory` 支持从目录或搜索结果开始，按需读取记忆正文。身份记忆在同名 Agent 的
会话间共享，房间记忆供本房间成员和协调者使用。内容仍保存在 Markdown 目录中；更新
需要读取时的版本，防止会话互相覆盖。编辑或删除主题会同步更新索引，每次模型请求前
刷新当前索引。记忆是可纠正的资料，不扩大执行权限；删除持久记忆也不清除已有对话记录。

`chat_read` 可以按关键词、讨论线程和序列范围缩小查询；`chat_session` 的 `results`
先返回结果索引，再按结果编号分段读取正文。这里提供最终结果，不向其他会话开放私有
推理或工具轨迹。旧版本没有保存的独立会话结果不会自动补录，用户仍可从会话详情查看历史。
模型自行判断需要哪些资料、是否保存记忆以及怎样继续工作，无需为每次交流建立固定流程。
