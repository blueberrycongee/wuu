# 子代理

Subagent 插件让 Agent 将边界明确的任务交给另一个模型上下文，并把结果带回父会话。使用前需要启用该插件。

## 明确委派范围

子代理适合独立调查、复核，以及文件归属清楚的改动。例如可以这样要求：

```text
并行调查两个导入路径为什么失败。两项调查都只读，返回相关文件和证据，
最后在这里汇总原因。
```

父 Agent 决定是否委派，并负责检查和整合结果。把很小的任务拆开，或让多个 Agent 修改同一批文件，可能增加沟通成本。每个子代理也会产生独立的模型请求和 token 消耗。

## 上下文独立不等于文件隔离

| 选项 | 效果 |
|---|---|
| 全新上下文 | 从任务说明开始，不继承父会话；这是默认方式 |
| 派生上下文 | 继承父会话，作为新任务的背景 |
| worktree 隔离 | 创建独立的 Git 工作目录；当前插件同时为此选项使用派生上下文 |

子代理默认共用工作区。仅使用全新上下文不会隔离文件。并行编辑时，应划清负责的文件或使用 worktree，并在开始前确定如何整合改动。

## 等待结果或并行继续

插件的 `spawn_agent` 工具默认在后台执行。父 Agent 可以处理其他工作，子任务完成后通过通知带回结果。插件提供相应界面时，输入框上方会显示子任务状态。

下一步立即依赖结果时，父 Agent 可以设置 `run_in_background: false`。工具会等待并直接返回最终状态、输出和错误。前台等待十分钟后仍未结束的任务转为后台执行，不会因此取消子代理。

## 补充要求或停止子任务

可以要求父 Agent 向指定子任务补充说明或取消任务。插件通过 `send_message` 发送后续输入，通过 `close_agent` 取消。停止父会话当前回复，不能替代明确取消子任务。

子代理仍受宿主的会话和权限规则约束。返回的结果是需要检查的证据，不是正确性的保证。整合前检查文件改动和测试；运行环境中断后，也不要假定任务已经完成。

子代理是模型会话；[后台命令](../reference/agent-command-system.md)是本机进程；[定时任务](../automation/scheduled-tasks.md)则负责在未来投递工作。三者用途不同。
