# Wuu 消息流阅读排版提案

日期：2026-09-10。本文保留最初的设计提案与参数探索；当前已完成第一轮产品改动，实际参数与截图见 [实现与验收记录](implementation-review.md)。

## 设计判断

把一轮回答组织为一篇可连续阅读的小文章：读者先看到问题，再识别过程状态，最后顺着稳定的左侧对齐线阅读结果。信息的重要性通过字号、字重、距离和展开状态共同表达。

借鉴新闻文章页的正文尺度、层级和留白。消息流仍然是单列、连续滚动的交互界面；正文保持系统无衬线字体，避免把报纸的多栏版式、巨大标题和密集装饰搬进工作区。

| 现有规则 | 位置 | 设计影响 |
| --- | --- | --- |
| 正文默认 14px / 1.75，字重 400 | `desktop/src/renderer/styles/conversation-shell.css` | 行距并不紧，优先调整字与行宽的比例 |

| 单轮外间距 48px，提问到回复 32px | `conversation-shell.css` | 已有良好的分组基础，应保留并消除子组件重复贡献 |

## 字号与字体

以下为待实测的设计起点，不是报刊网站的原样参数，也不是通用的最佳值。字号与行高成对定义，正文大小由现有用户设置控制。

| 角色 | 默认字号 / 行高 | 字重 | 规则 |
| --- | --- | --- | --- |
| 回答主标题 h1 | 20 / 30px | 600 | 仅在内容本来有主标题时出现 |
| 章节标题 h2 | 18 / 28px | 600 | 提供长文扫读锚点 |
| 小标题 h3–h6 | 16 / 28px | 600 | 保留语义层级，视觉尺度收敛 |
| 正文、用户提问 | 16 / 28px | 400 | 核心阅读层；中文、英文和行内代码混排 |
| 过程摘要、过程叙述 | 14 / 22px | 400 | 实质性结论与需要用户处理的错误仍按正文层级显示 |
| 时间、来源、附注 | 12 / 18px | 400 | 只放次要信息；明确的文字对比度 |
| 代码、日志、表格内容 | 14 / 22px | 400 | 代码用等宽字体，表格用系统无衬线 |

以用户设置的正文大小 B 为基准：正文 B；主标题 B+4；章节 B+2；小标题 B；过程与代码 max(12, B−2)；元信息 max(12, B−4)。所有层级使用无单位行高，随字体大小同步变化。正文默认 B=16，行高 1.75；元信息行高 1.5；过程与代码行高约 1.57。

保持现有系统字体回退栈，正文不额外加字距。常规强调使用 600；避免大段加粗。宋体或衬线体适合作为可选阅读风格先试在长回答标题，中文代码混排正文默认继续使用系统无衬线。

## 栏宽与对齐

- 外层工作区可保留 800px 宽度，供输入框、代码、表格和图表使用。
- 正文起始建议最大 640px：16px 中文约 40 字一行。短回答自然收尾，窄窗自动缩窄；英文占主导的内容可对比 65–75ch 的专门阅读尺度，不能把 ch 直接当作汉字数。
- 640px 是上限，不是固定宽度。窄窗保留 16px 边距，不通过缩小正文来挤内容。
- 标题、正文、过程摘要和宽内容块外沿共用主左侧对齐线。宽内容向右延伸；避免每个段落、标题或代码块各自居中。
- 输入框内部文字可与主左侧对齐线对齐，边框向外留出内边距。用户气泡保持右侧锚点，长提问限制正文行长。
- 普通段落无首行缩进、左对齐。列表使用悬挂缩进：换行后对齐第一行的文字，不对齐项目符号。

W3C 的 AAA 视觉呈现条款包含让用户获得 CJK 行宽不超过 40 字、非两端对齐等设置的机制。这里把它作为阅读宽度参考；本提案不宣称满足完整 AAA 条款。

## 间距系统

采用 4px 基础步进，但以内容关系命名。以下数值指最终块边缘之间的间距，只由一个布局层负责，不再叠加父级 gap 与子级 margin。

| 内容关系 | 起始值 |
| --- | --- |
| 图标与短标签 | 4–8px |
| 同一列表内的条目 | 8px |
| 标题 → 所属正文 | 8px |
| 正文段落 → 正文段落 | 16px |
| 介绍句 → 列表 | 8px |
| 列表/引用/代码 ↔ 相关正文 | 16px |
| 过程组 → 最终回答 | 24px |
| 前一章节 → 下一标题 | 32px |
| 用户提问 → 回复过程或正文 | 32px |
| 上一轮回答 → 下一轮提问 | 48px |

最重要的关系是：条目间距 < 段落间距 < 章节间距 < 会话轮次间距。正文行高从 24.5px 增至 28px 时，把段间 gap 从 24px 调到 16px，能同时保留行内呼吸与段落连续性；最终需要用真实长文确认。

标题前空间大、后空间小，使标题归属于下方内容。消息开头的标题不保留上间距。代码块、表格和来源模块不叠加匿名外边距。

## 缩进系统

只保留主线和两级内容缩进：0 / 24 / 48px。24px 在默认字号下对应 1.5em，随阅读字号变化；窄窗可降低到 1.25em。

- 一级列表文字相对主线内缩 24px，二级内缩 48px；符号占用悬挂区域。
- 引用边线落在主线，引用文字内缩 24px。
- 展开的过程详情只内缩一次 24px。里面的工具行不因组件嵌套继续累积 padding。
- 代码与表格外沿落在主线，其 16px 内边距属于容器，不视为新的内容层级。
- 更深层的原始列表应保留内容和语义；小屏收敛后续缩进，避免每层增加一整级宽度。可在生成内容规范中推荐最多两层，而非在渲染时删除深层内容。

## 视觉重心与运行状态

最终回答采用深色正文和干净背景。过程使用较小字号、紧凑行距和可折叠结构来降低权重，避免把文字淡到难读。用户长消息的整块黑底很醒目，可比较柔和中性底色；这是第二阶段的视觉选项，不是阅读系统生效的前提。

执行中保留最新进展及状态；完成后可将已完成操作收成摘要。用户主动展开的过程详情保持展开。失败、权限请求和待用户决策要维持明确的可见性。最终回答在流式与完成状态下共用排版规则，不在完成时突然改变宽度、字号和间距。

## 实施顺序与验证

1. 先统一正文、过程、代码、元信息的语义变量，并将过程固定 20px 行高改为随字体变化。现有字号设置需保留；评估默认值更新时已有用户是否明确选过 14px，不能直接覆盖其选择。
2. 将正文行宽与输入框宽度解耦，落地层级间距和悬挂缩进。标题保留原始 h1–h6 语义，并使用收敛的视觉尺度。
3. 检查 `.rich-content`、`.streaming-markdown-block` 内部及跨 block 的相邻关系；仅给外层配置 gap 无法覆盖全部流式 Markdown 场景。现有工作区文档预览和聊天气泡也共享 RichContent，应限定影响范围。
4. 最后比较用户气泡色块、过程摘要对比度、可选衬线标题等视觉细节。

用同一批内容比较修改前后：一行短答、800 字中文长答、中英路径混排、嵌套列表、跨流式分块标题、代码/表格、展开过程、错误与审批、长提问。覆盖窄分屏、常规桌面、深色主题和用户字号放大；确认无页面横向溢出、无裁切、复制操作可达，流式内容结束时不改变布局规则。

最初设计阶段仅产出了提案与 HTML 阅读样稿。样稿中的“现有规则近似”用于比较主要排版参数，并非当前界面的像素级复刻；后续产品改动与测试另见实现与验收记录。
